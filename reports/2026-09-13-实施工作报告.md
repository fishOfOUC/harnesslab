## 4. 关键实现说明

### 4.1 运行生命周期（文档 03 第 2、3 节）

`queued → running → waiting_approval → queued → … → completed/failed/cancelled`。所有对外可见状态先写业务表与事件表，再更新 run 状态，避免出现「已完成但无产物」的中间态。`waiting_approval` 释放执行槽位并保留检查点，等待时间不计入活跃时长但有独立过期时间（默认 24h）。

### 4.2 审批中断的真实链路

```
模型请求 create_demo_ticket
  → 工具网关按策略判定 REQUIRE_APPROVAL
  → 工具函数内 interrupt({tool_name, 规范化参数, 参数哈希, 预期影响, tool_call_id})
  → 执行器捕获 __interrupt__，写入 approvals（含 checkpoint_id）+ 发 approval.requested
  → run 转 waiting_approval，工作进程释放
用户批准（API 校验 revision + 参数哈希 + 有效期 + run 状态）
  → run 重新入队并带 resume 载荷
  → 执行器 Command(resume=...) 恢复图，工具继续执行，幂等键命中账本
```

工具账本幂等键 = `run_id + 逻辑动作 ID(tool_call_id) + 工具版本 + 审批参数版本`；**崩溃发生在「工单已提交、图节点未提交」边界时，恢复会复用已持久化结果，不会产生第二份工单**（已用测试固定）。

### 4.3 与框架的边界（ADR 实现期补充）

1. 审批不使用 `HumanInTheLoopMiddleware`：业务表需要记录参数哈希与修订版本，框架通用中断无法表达「一次批准只绑定一个参数版本」，两套并用会产生互不知晓的审批记录。
2. `create_agent` 编译图直接作为运行图；队列、租约、状态机、审批、恢复对账在 `runtime` 层显式实现，避免内外双层模型/工具循环冲突。代价是计划/收尾不在图检查点内（计划无副作用，重算安全）。
3. `RunExecutor` 通过 `model_factory` 注入模型，使控制流测试可用确定性替身，而生产使用真实 Chat 模型。

### 4.4 单进程约束的工程处理

Qdrant Local 只允许单进程访问目录，因此 `api serve` 默认内联工作进程（`RUN_WORKER_IN_API=true`），并在启动日志与 README 中说明：要独立 `worker serve`，需把 `VECTOR_MODE` 切到 `service`。这是对文档 02「API 不另开实例竞争该目录」的落地方式。

### 4.5 关于「不虚构精确性」

- 无本地 tokenizer → 保守公式估算，结果标注 `token_estimate_kind: estimate`
- 价格不可用 → 显示「费用：未知」，不填零
- 探测失败 → 能力字段保持 `false` 并给出原因，不假装可用
- 评测报告中生成质量、任务成功率等未跑项 → 写「未执行」而不是留空

## 6. 已知限制

1. **单机单进程**：单工作进程、SQLite、Qdrant Local；不承诺多工作进程共享本地向量目录。服务化迁移需数据导出校验、索引重建、检查点版本兼容与恢复演练，不只是替换连接串。
2. **计划与收尾不在图检查点内**：崩溃恢复时计划会重算（无副作用），但不会恢复「已完成步骤列表」的历史版本。
3. **重规划、重排、MCP、多 Agent、回放页未实现**，不能宣称支持。
4. **注入防护是辅助而非保证**：系统提示与不可信块标注已实现，模型是否被绕过需要对抗测试来度量。
5. **本机开发身份**：仅绑定 loopback；进入局域网/公网前必须实现正式认证与资源授权。

## A.4 联调中发现并修复的三个真实缺陷

三个缺陷在此前的 99 项测试与替身模型冒烟中**都没有暴露**，全部由真实链路暴露。

### 缺陷 1：共享 SQLite 连接未串行化（数据正确性）

- 现象：真实运行中出现 `search_knowledge` 偶发失败，错误为 `NOT_FOUND 文档不存在` 与 `TOOL_FAILED InterfaceError`。
- 根因：`Database` 使用单条连接，`transaction()` 有写锁，但 `query()/query_one()/execute()` **读操作未加锁**。工作进程执行运行的同时，API 线程池在轮询 `/runs/{id}` 与 `/timeline`，两个线程的语句在同一连接上交错，读到彼此的结果集。
- 证据：写了最小复现（4 读 1 写共享未加锁连接），稳定得到 `sqlite3.InterfaceError: bad parameter or other API misuse` 与读空记录，与真实运行症状一致。
- 修复：所有连接访问（读+写）共用一把可重入锁；`schema_version` 同样纳入。
- 回归：新增 `tests/test_concurrency.py`（6 个用例，3.6 秒）——读线程与写线程并发时校验行身份、事件 seq 唯一、租约竞争单一赢家、并发检索命中集合一致、随机交错无异常。

### 缺陷 2：引用映射在审批中断后丢失（功能正确性）

- 现象：真实运行的最终结果是「**引用 0 条**」+「引用了本次召回之外的标签，已从有效引用中剔除：S1…S11」，而模型明明在前一阶段检索并引用了这些来源。
- 根因：文档 03 第 4 节要求 `evidence_refs` 属于运行状态，但我把 `S1…Sn` 只放在 `ToolContext`（内存对象）里。审批中断后恢复会重建上下文，此前引用全部丢失；同时标签每次检索都从 S1 重新编号，跨检索本身就有歧义。
- 修复：标签改为**全 run 内全局唯一**（重复片段复用原标签），并在恢复时**从工具账本重建引用映射**（检索结果本就持久化在账本里，是权威记录）。
- 验证：真实模型重跑后引用 14 条、限制说明 0 条；新增两个回归用例（`test_citations_survive_approval_resume`、`test_citation_labels_are_global_and_stable`）。

### 缺陷 3：证据阈值口径错误（判定逻辑）

- 现象：混合检索模式下几乎永远判定"证据不足"。
- 根因：`min_evidence_score` 是余弦相似度量级（0.15），但混合模式拿 **RRF 融合分**（量级约 0.03）与它比较。
- 修复：证据强度统一取**本次召回中最强的向量余弦相似度**（跨模式可比），并通过 `evidence_score` 暴露给模型与检索实验室；融合分只用于排序展示。
- 同时修正评测口径：原先把"语料明确写了没有给出该保证"的题也算作"无答案题"，导致该指标恒为 0。现在只有数据集标注 `expects_insufficient_evidence=true` 的题进入分子分母，并补了一条语料完全未覆盖的真题（demo-006）。修正后无答案处理率 = **1.0**。

## A.7 经验总结

1. **替身模型能验证控制流，验证不了数据正确性**。缺陷 1（并发）与缺陷 2（引用跨中断）都是被"真实 + 多次 + 边轮询边执行"的组合打出来的。
2. **自测脚本本身也会骗人**：第一版并发测试写了"读线程等停止标志、停止标志等读线程"的自锁死，表现为卡住几分钟——这是测试设计的错，不是被测代码慢。写并发测试时必须给每个线程独立的、确定的退出路径。
3. **评测口径写错比功能写错更危险**：它会让人以为功能坏了（无答案率 0），也可能让人以为功能好了。指标定义必须连同数据集标注一起审。
4. **诊断要用最小复现证明**，不要停在"应该是并发问题"。这次用 15 行复现脚本拿到了与生产完全相同的报错，才敢下结论。
