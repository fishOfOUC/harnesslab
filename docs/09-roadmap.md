# 09 实施计划与任务清单

## 1. 交付原则

先完成可运行的单 Agent 闭环，再加入复杂协作与隔离执行。每个阶段交付可演示功能、自动化验证和更新后的说明；不能只添加依赖或界面开关就宣布支持某项能力。

以下工作量按一名熟悉 Python 与 Web 的开发者估算，属于规划区间，不是交付承诺。模型兼容、机器资源和 UI 完成度可能显著影响时间。

## 2. 阶段与退出标准

| 阶段 | 估计工作量 | 交付 | 退出标准 |
| --- | --- | --- | --- |
| M0 环境与契约 | 2–3 人日 | 脚手架、锁文件、配置、模型探测 | Chat/Embedding 分离可用，保存真实模型档案 |
| M1 最小问答闭环 | 4–6 人日 | 导入、向量检索、流式问答、引用、基础工作台 | 30 条最小评测可运行；引用可定位 |
| M2 可控执行 | 4–6 人日 | 持久任务、检查点、预算、工具网关、取消、故障恢复 | P0 核心控制测试全部通过 |
| M3 完整单 Agent | 4–6 人日 | 审批、报告、计划、上下文压缩、长期记忆 | 审批重启恢复且模拟工单不重复 |
| M4 扩展与协作 | 4–6 人日 | MCP、Skills、多 Agent、混合检索、检索实验室 | 扩展工具不绕过策略；父子任务可追踪 |
| M5 展示定版 | 3–5 人日 | 100 条评测、安全回归、演示资料、回放、排障说明 | 两次彩排通过，限制与实测成绩公开 |
| M6 进阶实验 | 另行估算 | 隔离代码执行、定时任务、多模态、服务模式、Deep Agents 对比 | 各能力独立验证后启用 |

M0–M5 合计约 21–32 人日。可先交付 M0–M2 作为可运行版本，完整展示目标在 M5 达成。

## 4. 依赖关系

Embedding 探测 → 索引指纹 → 导入与检索 → 引用问答 → 质量评测。

业务持久化 → 检查点与工具账本 → 审批恢复 → 可安全演示的写工具。

预算与权限 → 子任务协议 → 多 Agent；工具网关 → MCP；文件作用域 → 产物管理 → 隔离代码执行。

UI 可先以契约替身开发，但替身模式必须显式标识，最终验收换成真实后端。

## 5. 完成定义

每项任务应有对应实现、行为验证、错误路径和文档更新。涉及模型的任务附真实模型记录；涉及存储的任务经过重启；涉及副作用的任务经过重复请求；涉及 UI 的任务经过一次真实用户路径。

提交说明包含需求 ID、行为变化、验证结果和剩余限制。模型或依赖升级记录在变更日志中，不无声改变演示基线。

## 6. 风险与处理

| 风险 | 处理 |
| --- | --- |
| 只有 Embedding，未准备 Chat 模型 | M0 先解决，检索开发可独立推进 |
| 本地 Chat 工具调用不稳定 | 记录能力限制，更换已验证配置或展示受限模式 |
| 显存不足 | 批量减小、模型并发设为 1、错峰索引，实测后调整 |
| 功能范围扩大导致无法展示 | 以 M2、M3、M5 为可交付检查点，P2 独立排期 |
| 框架升级影响检查点恢复 | 锁定版本、保存图版本、旧运行受控迁移 |
| 评测只关注主观好看 | 保留固定数据集、失败样本和控制类硬断言 |
| 网络或云服务不稳定 | 本地资料、本地工具、明确标注的回放备用 |

## 7. 实施前需填入的信息

当前文档已按合理默认值完成，以下信息在 M0 填入即可，不影响设计阅读：

- 实际 Embedding 模型 ID、revision、前缀要求和实测维度。
- Chat 模型及服务地址，是否允许使用云端处理合成演示资料。
- 内存/显存、可接受延迟，以及是否可以使用 Docker Desktop。
- 展示受众与时长，优先突出 RAG、Agent 控制还是多 Agent。

不将尚未确认的模型名、硬件或接口能力写成既定事实。
